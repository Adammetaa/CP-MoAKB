# Knowledge Lab Prototype Boundaries

Status: Governing prototype note
Version: 1.0

## Authority

The static prototype is subordinate to the Knowledge Constitution, KAS-001
through KAS-007, KGS-001 through KGS-006, Knowledge Editorial Handbook,
Knowledge Review Framework, Canonical Knowledge Authoring Templates, ADR-005
through ADR-009, RAS-001 through RAS-015, Design Freeze, Source Policy, Evidence
Levels, Publication Boundary, Knowledge Workspace Blueprint, and Explorer
localization policy. It changes none of them.

## Product Boundary

This is a static experience prototype, not production software. It demonstrates
possible presentation of queues, roles, candidates, evidence, findings, versions,
decisions, gates, packages, and audits. Interface visibility is not permission;
role selection is not authentication; a button is not authority; a comment is
not a finding or decision.

## Engineering Boundary

The prototype defines no schema, Runtime behavior, parser, registry, validation,
public API, Python model, JSON Schema, YAML Schema, database table, backend
service, persistence, authentication, authorization, analytics, notification
delivery, workflow automation, or production frontend framework. It loads no
third-party JavaScript, font, asset, or CDN resource.

## Knowledge and Safety Boundary

All content is a fictional placeholder with no agricultural assertion or
real-world referent. Uploaded PDFs are not read. The prototype does not infer,
score, rank, diagnose, recommend, generate knowledge, interpret regulation, or
establish terminology or ontology authority.

Required notices remain explicit: candidate is not accepted knowledge; candidate
and evidence are not diagnosis; knowledge and candidate are not recommendation;
acceptance is not publication; publication is not regulatory permission; UI
status is not scientific confidence; operational priority is not scientific
importance; discussion is not decision; translation is not accepted terminology.

## Publication Boundary

Knowledge Lab may depict release preparation only. It cannot push, tag, create a
GitHub Release, deploy, release a package, publish public data, or publish to
Knowledge Explorer. Separate governed authority and a separately implemented
process would be required.

## Change Control

Prototype changes require product, accessibility, localization, governance,
security, publication-boundary, and architecture review. Future implementation
requires explicit owner authorization and new engineering decisions.
